# Toolkit.Tourney

`Toolkit.Tourney` stores a competition definition separately from its playing state. A definition contains participants, stages, scheduling rules, scoring rules, and routes into later stages. `TCompetitionEngine.Initialize` creates fixtures; `RecordResult` updates results and standings and starts downstream stages when their inputs are ready. Definitions and state can be serialized with jconv.

The module is split by responsibility: `model.bmx` holds the serializable model; `tourney.bmx` holds the engine, interfaces, and serializer; `groups.bmx`, `league.bmx`, `brackets.bmx`, and `series.bmx` implement formats; `ordering.bmx` handles draws and individual-stage calendar slots; `calendarplanner.bmx` searches slots across started stages; `roundrobin.bmx` and `scores.bmx` contain shared algorithms; `seriesranking.bmx` ranks series tables; `clinching.bmx`, `qualification.bmx`, and `seriesqualification.bmx` analyze remaining scoring possibilities; `timeline.bmx` records standings after each result.

## Observe a competition as it plays

Implement `ICompetitionResultObserver` and pass it to `TCompetitionEngine.AddResultObserver` to receive `OnResultRecorded` after each successful `RecordResult` call. The callback receives the competition, its updated state, the stage and fixture IDs, and the recorded payload. Standings, stage completion, and any downstream stages started by advancement are current when it runs. This works for every result format and lets applications collect snapshots or update a visualisation without putting display logic in a scorer. Observers are attached to the engine, not serialized with the competition state; register them again when resuming. Treat the callback's state as read-only. An observer exception propagates after the result has been applied.

The [2024 Tour replay](../examples/tour_2024_replay.bmx) uses this hook to export the daily standings read by its viewer. Its saved snapshot file is unchanged by the move from a replay-specific callback.

## Correct a recorded result

`RecordResult` now saves an ordered action journal and a pre-result state snapshot in `TCompetitionState`. Both survive jconv serialization. Call `engine.CorrectResult(comp, state, stageId, fixtureId, replacement)` to rebuild the competition from that snapshot, replacing one recorded fixture result. The method returns `TResultCorrection.state` and a list of `invalidated` actions. Keep the returned state; the input state is not changed. Valid later results are replayed in order. A later result whose fixture or entrants changed is left unapplied and listed for review, which prevents an old score from being assigned to a new matchup. Invalid replacement results leave the original state untouched.

The definition used for replay must be the same one used when recording the journal. A journal begins with the first result, schedule revision, or table tie decision recorded by this version; results already present in an older saved state cannot be corrected through it. The snapshot includes caller-supplied draw and schedule changes made before that first action. Later direct changes to fixture assignments are outside the journal; use `ReviseFixtureSchedule` for changes that must survive replay. Random state at the first action is saved so progressive draws replay consistently. `TCompetitionTimeline` resets and rebuilds its frames after a successful correction. Other registered result observers must implement `ICompetitionReplayObserver.OnReplayReset`; correction rejects an observer that cannot clear its earlier output. The journal serializes result payloads with jconv; call `engine.SetJournalConverter(converter)` when a custom payload needs a registered serializer, and use the same converter when correcting it.

## Resolve a table tie

Built-in group, league, and points-based series rows expose `sportingRank`. Rows still tied after every configured criterion share that rank; participant ID only stabilizes their displayed order. A group or series advancement route selecting some but not all members of such a tie leaves its destination pending. A `BestXAcrossGroups` cutoff likewise waits when points, score difference, and scores for are equal. A season movement crossing a tied rank raises an unresolved-tie error.

For a completed stage, `engine.UnresolvedTableTies(comp, state, stageId)` returns the undecided tied sets from its tables. Each item supplies `stageId`, `scopeKey`, and the exact `participantIds`; the order is the current display order, not a decision. The query leaves the supplied state untouched. It also reports a `"bestAcross"` set when that cross-group cutoff currently blocks advancement.

Call `engine.RecordTableTieDecision(comp, state, stageId, scopeKey, orderedIds, reason)` with the entire tied set in the desired best-to-worst order. Use an empty `scopeKey` for the main table, a group key such as `"A"` for a group table, `"bestAcross"` for a cross-group cutoff, or a named series championship code. A cross-group decision must match the exact set blocking the active route. The method validates the tied participants, returns a new state, and retries advancement. It rejects a new decision after a dependent stage has started, because its earlier seeding could already depend on the old order. Keep the returned state for later results. The decision and reason are saved in the ordered replay journal; if a corrected result removes the tie, replay invalidates the decision. Existing custom scorers that supply their own ordered rows are unaffected unless they assign `sportingRank` themselves.

`ETiebreaker.FairPlay` compares the sum of nonnegative `TResultPayload.fairPlayHome` and `fairPlayAway` penalty units recorded on completed head-to-head fixtures; lower is better. `ETiebreaker.RandomDraw` must be last and requires an explicit table tie decision if the preceding criteria still tie. The application conducts the draw; the engine records its order and reason.

## Revise a live schedule

Call `engine.ReviseFixtureSchedule(comp, state, stageId, fixtureId, slotId)` for an unplayed scheduled or postponed fixture. It returns a new state and leaves the input untouched. The requested slot is pinned while the joint planner checks week rules, team availability, and venue conflicts across started stages. A successful revision returns a scheduled fixture and becomes an ordered journal action, so a later result correction reapplies it. Completed and in-progress fixtures retain their slots. Pass `round` when a league fixture must move to a particular week; a slot with its own round supplies that week when `round` is zero. Pass `replanFlexible = True` to release other scheduled or postponed fixtures for reassignment, such as when two teams sharing a stadium need to exchange slots. The optional `maxSearchNodes` bounds this search. An infeasible request raises an error without changing the supplied state. Keep the returned state before recording further results.

For a ready-made history, add a `TCompetitionTimeline` as an observer. Every `TStandingsFrame` has the stage and fixture IDs, event and session codes where available, the recorded score or classification, a copied set of group tables, and independent copies of the stage leaderboard and named championship boards. `frame.Board("DRIVERS")` retrieves a named board; `frame.Board()` retrieves the stage board. `timeline.Participant(id)` supplies a copied participant name, kind, group or division ID, and parent team ID. Earlier frames do not change when later results are recorded. The timeline is an in-memory application object rather than part of the jconv competition state.

## Compose a competition

`TCompetitionBuilder` is a small convenience for assembling the existing model. `AddStage(id, stageType, config)` creates an independent root; `Connect(sourceId, targetId, rule, outcome, mapping)` adds both an advancement route and the target's dependency. Use the existing `TFilterRule`, `EAdvancementOutcome`, and `TAdvancementMapping` values for selection and placement. `DependOn(sourceId, targetId)` records a dependency when the destination already selects its own entrants, such as a postseason pool. `AppendStage` accepts a fully configured stage when the convenience method is too narrow. `Build()` checks IDs and the stage graph and returns an ordinary `TCompetition`, which can be saved with jconv. The builder has no rendering or playing-state role; engine format handlers are still registered separately.

For common structures, `AddGroups`, `AddBracket`, and `AddSeries` create configured stages; `ConnectTop`, `ConnectBestAtRankAcrossGroups`, and `ConnectOutcome` create advancement routes. `TTourneyAuthoring` can also make group, bracket, and series configs, position scoring tables, bonuses, events, and selection rules independently of a builder. The point helpers take decimal strings and check that `pointsScale` can store them exactly. These helpers return the same model types as manual configuration, so callers can continue setting specialised rules on them.

Call `builder.Check()` to collect `TAuthoringIssue` values with stage, field path, and message for common configuration mistakes before play starts. `BuildChecked()` rejects the first such issue. `Build()` retains its graph-only validation for existing definitions. This preflight covers the supplied built-in group, bracket, series, and Swiss fields; sport-specific scheduling and result checks still run in their format handlers.

For example, two four-team groups feeding a final can be assembled with `AddStage("GROUPS", EStageType.Group, groupConfig)`, `AddStage("FINAL", EStageType.Bracket, finalConfig)`, and `Connect("GROUPS", "FINAL", topOnePerGroup)`. The connection makes `FINAL` wait for `GROUPS` and adds the selection route. Stages with no connection remain independent roots, so several competitions can start together before merging later.

[The small builder example](../examples/builder_example.bmx) creates and plays that structure using the helpers and `BuildChecked()`. The preflight catches common definition errors; format-specific scheduling and result requirements are still checked when the engine starts or receives results.

Stages form a directed graph. `TStage.input.fromStageId` or `fromStageIds` names required predecessors; `TStage.advancement` selects entrants for a destination. A stage with `independent = True` starts alongside other root stages. A target waits for every named predecessor, retaining received entrants in `TStageState.inputs` so the state can be saved between results. If no explicit relationship exists, the previous stage in the array remains the source for older definitions.

Use a separate stage when a format has a distinct set of fixtures or advancement rule: a league followed by promotion playoffs, group play followed by knockout rounds, or parallel competitions feeding a final. An advancement filter can select `TopN`, `BottomN`, `ByRank`, or `BestXAcrossGroups`; `startRank` supports ranges such as ranks 3 through 6.

For `BestXAcrossGroups`, set `startRank` to select that exact rank from each group before comparing them across groups. For example, `startRank = 3` with `n = 8` selects the eight best third-place teams. Zero keeps the older behaviour of considering every entrant not already selected. Rank-specific selection requires group tables.

For bracket stages, set `TAdvancement.outcome` to `Winner` or `Loser` to route either side of each completed tie. This supports, for example, semifinal winners going to a final while semifinal losers go to a third-place match. `AllEntrants` forwards both sides, which the conditional reset match uses. The default `Selected` retains the existing filter behavior. Each route has one destination; a stage can declare several routes to different destinations.

`TAdvancement.mapping` controls placement in a destination bracket. `FixedSlots` takes one numeric, one-based draw position in `toSlots` for each selected entrant, in the same order. Positions 1 and 2 form the first tie, 3 and 4 the second, and so on. `Seeded` orders all received entrants again using the destination's seeding policy. `Partition` assigns entrants to the `"left"` or `"right"` half of the draw. A destination can wait for several source stages, and its received entrants and slot assignments survive jconv state serialization. Invalid or duplicate slot assignments raise an error when the destination is started. These mappings apply to built-in bracket destinations.

`ConditionalSlots` chooses a placement case from the completed source group tables. Set `qualifyingRank` to the group place whose qualifying *group combination* determines the case, then provide `conditionalCases`. Each `TConditionalSlotCase.qualifyingGroupKeys` is an exact, order-independent set; its `TGroupRankSlot` assignments identify entrants by group key and final group rank, with a numeric destination `slotId`. Put placements shared by every case in `baseAssignments`. The engine selects one matching case after advancement has chosen entrants and rejects a missing or ambiguous case, an unqualified entrant, duplicate assignments, and incomplete or invalid slots. Cases and assignments are ordinary jconv-serializable definition data. This handles published lookup tables without binding a bracket to participant IDs or result order.

## Elimination trees

`TEliminationTreeBuilder.Append` adds a complete knockout stage graph to a competition. Set `TEliminationTreeOptions.size` to a power of two and choose `SingleElimination` or `DoubleElimination`. A single-elimination tree has one stage per round and can include placement matches. A double-elimination tree has winner and loser rounds, a grand final, and by default a reset match if the undefeated winner-bracket entrant loses the grand final. The reset stage receives both finalists; it is marked `Skipped` when it is unnecessary. `TEliminationTree.ChampionId(comp, state)` returns the winner of the deciding match, or zero until there is one.

For example, with eight entrants and `idPrefix = "CUP"`, double elimination creates `CUP_W1` through `CUP_W3`, `CUP_L1` through `CUP_L4`, `CUP_GF`, and `CUP_RESET`. The builder routes eliminated entrants into the lower bracket and places incoming entrants across its ties. `grandFinalReset = False` selects a one-match grand final.

For single elimination, `thirdPlace = True` adds `CUP_THIRD` from the semifinal losers. For a wider classification ladder, set `placementThroughRank` to the last place you need resolved. An eight-entrant draw with `placementThroughRank = 8` creates matches for places 3–4, 5–8, 5–6, and 7–8. With `placementThroughRank = 6`, it resolves places 1–6 and leaves seventh and eighth unranked. The generated `TEliminationTree.PlacementId(comp, state, rank)` returns the participant at a resolved place, or zero while it is undecided; `Placements` returns an array of all places. The returned tree manifest can itself be serialized with jconv.

Set `seeding`, `matchFormat`, and `policy` on the options to share those rules across generated stages. With no `fromStageId`, the tree starts with all competition participants and `size` must match their count. Set `fromStageId` to feed its first round from an earlier stage; add an advancement route on that stage if only selected entrants should continue. The builder appends serializable `TStage` definitions, while the returned `TEliminationTree` holds the generated stage IDs and champion lookup method. Stage IDs must not already exist in the competition.

The old `TBracketConfig.format = DoubleElim`, `doubleElim`, and `consolation` fields do not construct an elimination tree. The built-in bracket scheduler rejects those settings; use the tree builder or define the connected stages explicitly.

## Seeded, random, and constrained draws

Set `TParticipant.seedRank` to an explicit positive ranking. A bracket with `ESeedingMethod.Ranking` puts the highest ranked entrants in separate pathways: in an eight entrant draw, ranks 1 and 2 can only meet in the final. Older definitions without `seedRank` retain positive participant ID as the ranking fallback. `ESeedingMethod.Random` shuffles every entrant without protecting any ranking. `ProtectedTopN` keeps a specified number of top ranks fixed and shuffles the rest.

`TSeedingPolicy.seedBands` permits a ranked draw with random placement *within* bands. For eight entrants, `[1, 1, 2, 4]` fixes ranks 1 and 2 in opposite halves, draws ranks 3 and 4 between their two positions, and shuffles ranks 5 through 8. The bracket records first round match positions, so later bracket stages with `reseedEachRound = False` keep their original lanes. Set it to `True` to pair surviving entrants again by rank. Bye entrants are carried into their correct next round positions.

For group draws, `TParticipant.drawPot` is distinct from division and region. Set `TDrawConstraints.maxFromPot = 1` to limit each group to one entrant from any pot. This can be combined with region limits, prohibited pairs, and other existing group placement constraints. An impossible allocation raises an error.

Register each format the definition uses on `TCompetitionEngine` through `RegisterScheduler`, `RegisterScorer`, and, when it advances entrants, `RegisterAdvancer`. A new sport or format can use `TStage.formatCode` and `RegisterFormat` without adding another value to `EStageType`. Its scheduler creates fixtures, its scorer interprets results and computes standings, and its advancer selects entrants. `EResultKind.Custom` with `TResultPayload.customCode` permits a registered scorer to handle a new result structure. For a custom `TConfig` subtype, set `configCode` and register an `IConfigFactory` on `TConfigSerializer` before reading jconv data.

## League matchups and weeks

`TLeagueScheduleConfig.matchupRules` builds a fixture list from division pools. Each rule selects source and target divisions and a mode:

| Mode | Pairing |
| --- | --- |
| `AllPairs` | Each participant in the source pool plays each in the target pool. |
| `SameRank` | Pair participants with equal nonzero `previousRank`. |
| `RotatingDivision` | Pair a source division with one target division chosen by `rotationSeed` and `rotationOffset`. |
| `RotatingDivisionPairs` | Pair every division in one even-sized source pool with exactly one other division, cycling through every division pairing over `pool size - 1` seeds. |

Combine rules to describe, for example, within-division games, rotating cross-division games, and rank-matched games. `RotatingDivisionPairs` takes an ordered `sourceDivisionIds` list with an even number of unique divisions and no `targetDivisionIds`; `rotationSeed + rotationOffset` chooses the pairing round. `gamesPerPair` controls repetitions. `sameRankOnly` adds a rank filter to any mode, including either rotation mode; participants need equal, nonzero `previousRank`. Set `excludeAlreadyScheduled` on a later rule to omit participant pairs produced by earlier rules. Rule order therefore matters when this option is used. `totalGamesPerTeam`, when set, is checked against the generated fixtures. `balanceHomeAway` orients generated rule fixtures so every participant hosts either half their games or one more/less, with repeated meetings split reciprocally whenever possible. It does not alter `fixedFixtures`, and it does not constrain home/away streaks within the eventual week order. For a published or unusually asymmetric schedule, supply `fixedFixtures` instead. The older `vsSameConference`, `vsOtherConference`, and `strengthSchedule` fields are rejected if set; express those pairings with `matchupRules` so the configured behavior is explicit.

`weeks` sets a fixed season length; zero lets the allocator add weeks. `byeWeeks` excludes a participant from a week. `minWeeksBetweenMeetings = 1` requires one intervening week between meetings of the same two participants, regardless of which is home; larger values require more intervening weeks, and zero disables the rule. It is a hard constraint: an infeasible fixed-length schedule raises an error. Each participant gets at most one fixture per week. A fixed length uses constraint search when assigning unpinned fixtures, and preassigned weeks are validated. When adding weeks to an open-ended schedule, the allocator checks byes and rematch gaps before assigning a fixture. The default allocator is intended for pairing and week constraints. Applications needing additional policies, such as broadcast windows or travel limits, can register an `ILeagueWeekAllocator` on `TLeagueScheduler`.

`TStage.schedule.calendar.slots` supplies candidate venue and time slots. The default calendar allocator checks participant overlap, venue overlap at the same `dateTime`, `TParticipant.homeVenueId`, `TTeamBlackout`, and optional `TSlot.round`. It also respects reservations from other stages already scheduled in the same competition, so two teams sharing a stadium cannot both host at the same time across independent stages. Within the new stage it searches candidate assignments instead of relying on the first available slot; `TCalendar.maxSearchNodes` bounds that search. An impossible assignment and a search-limit result produce different errors, and a failed search leaves no partial new assignments. A custom `IFixtureSlotAllocator` can enforce more detailed rules; implement `ICompetitionSlotAllocator` as well to receive cross-stage reservations.

For fixtures already known when a competition starts, call `engine.Initialize(comp, True)` to generate every root stage's fixtures before placing them. The built-in joint planner chooses weeks and slots together for fixed-length league stages with calendars. It can also do this for open-ended leagues when **every** calendar slot has a positive `round` (week) number; those slots bound the search, and the planner tries shorter schedules first. When an open-ended calendar contains any unnumbered slot, the existing league week allocator chooses weeks before joint slot planning. Joint week planning respects preassigned weeks in `fixedFixtures`, byes, one-game-per-week limits, and rematch gaps. It searches slots across started stages, choosing the most constrained fixture first and backtracking when an earlier choice blocks another fixture. For stages with 3 to 32 unplaced fixtures and at most 64 slots, a distinct-slot matching check detects when all remaining fixtures cannot fit their available slot IDs, even if each fixture has an individual choice. Additional bounds check whether each league participant has enough available weeks and whether fixtures forced to one physical venue have enough distinct start times across all stages. Those bounds run at the root for large schedules and at every search node for smaller schedules. They prove some shortages early; backtracking still handles other conflicts. Slot rules include round, home venue, blackout, participant overlap, and shared venue. For an existing state, `engine.PlanSchedule(comp, state, True)` may reassign both weeks and slots of unplayed fixtures, except weeks pinned in `fixedFixtures`. `engine.PlanCalendar(comp, state, True)` changes slots only. Omit `True` to preserve existing assignments. Both methods return the number of fixtures assigned and accept a `maxSearchNodes` search bound. A failed search restores previous round, slot, and venue fields and reports either the search limit or a blocked fixture with candidate reasons. `engine.lastScheduleFailure` contains a structured `TScheduleFailureReport` after a search failure: stage and fixture IDs, assigned-fixture count, candidate week/slot labels and rejection reasons, nodes searched, and whether the node limit was reached. `capacityConflict` marks a proven shortage; `capacityKind`, `capacityResource`, `requiredFixtures`, and `availableResources` describe week or shared-venue shortages when applicable. The report is a representative dead end, not a proof that its reasons form the complete or minimal conflict. Joint planning requires the built-in slot and league week allocators.

The [shared-stadium example](../examples/shared_stadium_planner.bmx) shows two independent stages competing for the same venue, with the planner moving the flexible fixture to leave the scarce slot available.

### Scheduling preferences

Set `TStage.schedule.preferences` to a `TSchedulePreferences` value to rank feasible joint schedules. `minRestWeeks` and `restShortfallWeight` charge each missing idle week between a participant's games. `maxHomeStreak` and `maxAwayStreak`, with `streakExcessWeight`, charge each game beyond a preferred consecutive home or away run. `venueTransitionWeight` multiplies the directional `TVenueTransitionCost` entries for travel between consecutive game venues; unlisted transitions cost zero. Streaks and travel follow fixture week order, then slot `dateTime` order within a week. Rest costs apply only when both fixtures have positive week numbers. These costs are stage-local and optional; zero weights disable them. The existing hard scheduling rules still determine whether a schedule is feasible.

With preferences enabled, the planner searches for the lowest total cost; for open-ended leagues it first seeks the shortest feasible season, then the lowest cost within it. A valid existing schedule becomes the initial candidate when replanning, so a bounded search preserves it unless it finds a better candidate under that ordering. The search prunes a branch when the exact costs of fully placed participants plus unavoidable rest costs already meet the best candidate. `TCompetitionEngine.lastSchedulePreferenceScore` gives the selected cost, `lastSchedulePreferenceOptimal` says whether the result was proved optimal, and `lastScheduleSearchNodes` and `lastSchedulePrunedNodes` expose search effort. If `maxSearchNodes` is reached after finding a feasible schedule, the planner returns its best candidate and sets `lastSchedulePreferenceOptimal` to false. If it finds none, it raises the search-limit error and restores the previous assignments. Venue travel costs are supplied by the caller rather than inferred from geographic distance.

### Toward a full schedule generator

The existing matchup rules generate opponents and can balance home assignments, while the joint planner places known fixtures into league weeks and calendar slots and can optimize configured rest, streak, and travel costs. A 32-team, eight-division test constructs a 17-game opponent formula with rotating within-conference division pairs, rotating cross-conference divisions, rank-matched residual games, and eight or nine home games per team. The division-pairing rule also has a five-season test for a six-division pool. Further work could explain unavoidable constraint conflicts more precisely, add reproducible random alternatives among equally scored schedules, and use stronger pruning or an external optimization solver for large instances.

## Swiss rounds

Register `TSwissScheduler` and `TSwissScorer` for an `EStageType.Swiss` stage with `TSwissConfig`. Set `rounds` before starting. Only the first round is created at initialization; the engine generates each later round after all results from the preceding round have been recorded. Pairings use current points, prefer nearby scores, and avoid repeat opponents when `avoidRematches` is enabled. `colourBalance` chooses the home/away (or white/black) orientation that best balances the recorded history; it is a preference, not a guarantee. `maxRepeatPairAttempts` bounds the pairing search and produces a distinct limit error. This is a general Swiss policy, not a certified FIDE Dutch, Burstein, or other named pairing system.

Set `pairingPolicy.system = ESwissPairingSystem.DutchStyle` to use a separate deterministic, Dutch-inspired search. In the first round it pairs the upper and lower halves of the seed order. Later rounds prefer opponents on equal scores, try lower-half transpositions before exchanges, enforce no rematches, and reject same absolute colour preferences for non-topscorers. For an odd field it prioritizes the lowest eligible score for the pairing bye, then the fewest unplayed rounds. `pairingPolicy.initialColour` is `1` when the higher seed in the first pair receives home/White and `-1` for away/Black; the initial choice should be made by lot. This policy follows selected rules from the [FIDE Dutch system effective February 2026](https://handbook.fide.com/chapter/C0403202602), but does not yet implement its full bracket, floater, candidate-priority, or colour-allocation procedures. It must not be used as an exact FIDE Dutch pairing generator.

An odd field receives one completed bye fixture per round (`awayTeamId = 0`), worth `byePoints`; the same entrant is not given a second pairing bye. Bye fixtures need no result or calendar slot. `pointsScale` converts configured win, draw, loss, and bye points to exact integer standings units; its default of `2` preserves half points. `TLeaderboardRow.points` contains those units. With no `initialSeeding`, entrants start in `seedRank` order, falling back to participant ID. Set `initialSeeding = "random"` with a nonzero `TStage.schedule.scheduleSeed` for a reproducible random first round. The empty `pairingPolicy` placeholder is rejected rather than silently ignored.

Set `TSwissConfig.tiebreaks` to an ordered list of `ESwissTieBreak.Buchholz` and `ESwissTieBreak.BuchholzCut1`. Both values are stored in each row's `metrics` as `"buchholz"` and `"buchholzCut1"`, in the same scaled units as points. Use `TSwissConfig.plannedUnplayed` to specify a participant, round, `RequestedBye` or `Withdrawal`, and awarded points before the round is generated. Requested byes award zero or draw points; a withdrawal awards zero and excludes the entrant from that and every later round. For a forfeited pairing, submit a decisive head-to-head score with `TResultPayload.forfeit = True` through `RecordResult`.

Buchholz follows the [FIDE 2026 unplayed-round adjustments](https://handbook.fide.com/chapter/TieBreakRegulations032026) for these cases: an opponent's final requested bye or withdrawal is evaluated as a draw, while one followed by later non-voluntary play retains its awarded score. An unplayed round contributes the recipient's score, capped at `pointsDraw * rounds` for a bye or at the scheduled opponent's adjusted score for a forfeit. Cut 1 removes the lowest voluntary unplayed contribution when present, otherwise the lowest contribution overall. During an unfinished tournament these metrics are provisional because opponents can still earn points or resume play.

Fixtures, including byes, hold the round, opponents, home/away sides, and results. Saving and loading `TCompetitionState` therefore preserves everything needed to generate the next round. If a strict pairing or calendar rule prevents that generation after the last result of a round, the completed result remains recorded. Adjust the configuration or available slots and call `TCompetitionEngine.GenerateNextRound(comp, state, stageId)` to retry. A tie left after every configured Swiss tie-break is displayed in participant-ID order, not settled as a sporting result.

## Cycling stage races

Use `TCyclingConfig` with `engine.RegisterFormat("cycling-stage-race", New TCyclingScheduler, New TCyclingScorer)` for a race with successive stages and several classifications. Configure each stage's finish points, finish time bonuses, and checkpoint rules independently. A checkpoint may award sprint points, mountain points, or time bonuses; mountain point tables and young-rider eligibility belong to the competition config. `ridersPerTeam` selects how many of each team's fastest stage times count towards its daily team result. The next stage contains only riders who finished the previous one.

Record each stage as a custom `cycling-stage` result with one `TCyclingRiderResult` per active rider, plus results for every configured checkpoint. Raw stage time, credited GC time adjustment, time bonus, time penalty, and time-trial hundredths are separate values. Configured finish and checkpoint bonuses determine GC time; set `bonusRecorded` to check a published bonus against those rules. Signed rider point and team-time adjustments record official rulings without rewriting a stage finish. The engine rebuilds the general, points, mountains, young-rider, and team tables after every stage. GC ties compare time-trial hundredths, sum of stage places, then final stage place. Points ties compare stage wins, sprint wins, then GC rank. Mountain ties compare summit wins by configured category priority, then GC rank. Team ties compare counts of stage team placings, then the best GC rider. The general, youth, and team tables expose exact `TLeaderboardRow.timeSeconds`; points boards use integer units according to `pointsScale`.

The [2024 Tour de France replay](../examples/tour_2024_replay.bmx) uses [ASO's official stage and daily ranking tables](https://www.letour.fr/en/history) and the [2024 regulations](https://storage-aso.lequipe.fr/ASO/cycling_tdf/tdf24-reglement-fr-en.pdf). Its [saved results](../examples/tour_2024_official.tsv) cover all 176 starters, 21 stages, sprint and mountain checkpoints, withdrawals, time bonuses and penalties, official GC time credits, points deductions, and a team-time correction. It checks the full published final order and totals for all five classifications: 141 GC finishers, 123 points scorers, 58 climbers, 31 young riders, and 22 teams. Combativity is a jury award and is outside these calculated tables.

The saved roster includes every rider's name. The [Max2D Tour viewer](../examples/tour_2024_viewer.bmx) animates changes in rank between stages, with a stage selector, autoplay, and the stage podium. Keys `1`–`5` show the five season classifications; `6` shows that day's stage results. The `STAGE` column in rider classifications shows each rider's daily finishing place, even when the overall order stays the same. Click a rider to highlight and follow them through later stages and classifications; click them again or press `C` to clear the selection, and press `F` to bring them back into view. Scroll the standings with the mouse wheel while the pointer is over the main list, or use Up and Down. It reads [daily snapshots](../examples/tour_2024_snapshots.tsv) exported from the engine's standings and stage results. To regenerate the snapshots, build and run [the standalone exporter](../examples/tour_2024_export_app.bmx), then build and run `examples/tour_2024_viewer.bmx`. The viewer can also be run with `--check` to validate its snapshot file without opening a graphics window. The [exporter implementation](../examples/tour_2024_snapshot_export.bmx) is shared with the test runner, which still supports `--export-tour`.

## Fleet sailing regattas

Register `engine.RegisterFormat("regatta", New TRegattaScheduler, New TRegattaScorer)` and use `TRegattaConfig` on a stage with `formatCode = "regatta"`. Configure the number of scheduled opening races, the minimum needed to complete the regatta, the number and threshold of discardable worst scores, and optionally a medal race with a qualifier count and point multiplier. Races are generated one at a time. Record a complete fleet result with `TResultPayload.kind = EResultKind.Custom`, `customCode = "regatta-race"`, and one `TRegattaRaceScore` per entrant. Record an unrun race as a `StatusOnly` cancellation or abandonment; it remains in the schedule but contributes no points. The medal field is selected from the ranked opening series after the last scheduled race is resolved.

Low-point scores derive from finishing place. Common non-finishing codes use fleet size plus `penaltyOffset` (default one); `penaltyCodes` can replace that code set. For a discretionary penalty or redress, supply `scoreUnits` explicitly. `pointScale` defines exact units per point, so a scale of ten stores 10.2 points as 102 units. `DNE` and explicitly marked `nonDiscardable` race scores cannot be discarded. Medal scores are multiplied and never discarded. Equal totals compare counted race scores best to worst, then race scores from latest to earliest, including discards. Medal qualifiers stay ahead of nonqualifiers when `medalRanksAhead` is enabled; this matters when a nonqualifier's opening score is numerically below a medal racer's final score. `TRegattaStanding` preserves each race's score and discard flag; the standard leaderboard stores points in the same configured units.

The [Paris 2024 men's dinghy replay](../examples/paris_2024_mens_dinghy_replay.bmx) reads the [World Sailing results](../examples/paris_2024_mens_dinghy.tsv), reproduces all 43 sailors' eight opening race scores, records races 9 and 10 as abandoned, selects the published top ten for the medal race, and checks every final rank and point total against the [official results centre](https://paris2024.sailing.org/racing/results-centre/). This also exercises black-flag and other coded scores, exact fractional penalties, discards and the medal race ranking boundary.

## Timed heats and a final

`THeatsScheduler` and `THeatsScorer` provide a separate format for timed sports such as track racing and swimming. Register them together with `engine.RegisterFormat("timed-heats", New THeatsScheduler, New THeatsScorer)`, then set the stage's `formatCode` to `"timed-heats"` and its config to `THeatsConfig`. For one qualifying round followed by a final, configure `heatCount`, `automaticPlaces` per heat, and `fastestRemaining` across the other finishers. For heats, semifinals, and further qualifying rounds, set `qualifyingRounds` to an ordered array of `THeatRoundConfig` values with those fields; the final follows the last configured round. Each round is generated after the preceding round's results are complete. Entrants are distributed across heats in a seed-order snake in the first round and a qualifying-time snake thereafter. Each fixture's `heatEntrants` stores its assigned athletes; a timed result must include all of them, using `DNS`, `DNF`, or `DSQ` for nonfinishers.

Set a round's `fixedGroups` to an array of `THeatGroup` entries when its heat assignments are already known. Each group lists the participant IDs for one heat in heat order. This works for the first round, a repechage, or a later qualifying round. Generation checks that every eligible entrant appears exactly once, so a published draw cannot silently include someone who failed to qualify. If omitted, the scheduler uses its normal snake assignment. The [Paris 2024 men's 800m replay](../examples/paris_2024_mens_800m_replay.bmx) uses this option and the [official Athletics Results Book](https://iaafmedia.s3.amazonaws.com/misc/olympics/OG2024_ATHLETICS.pdf) to reproduce all six opening heats, four repechage heats, three semifinals, and the final from [published results](../examples/paris_2024_mens_800m.tsv).

Set a qualifying round's `repechage` to another `THeatRoundConfig` to add second-chance heats before the next main round or final. With the one-round shorthand, set `THeatsConfig.repechage` instead. Athletes who qualify directly skip repechage; finishers who miss direct qualification enter it; `DNS`, `DNF`, and `DSQ` entrants do not. The repechage rule independently sets its heat count, automatic places, fastest remaining places, and cutoff tie policy. Its qualifiers join the direct qualifiers for the next round. Direct qualifiers are ordered by their main-round times before repechage qualifiers, who are ordered by their repechage times; that combined order seeds the next round's snake. If nobody needs the repechage, it is skipped. This follows the [direct and repechage paths introduced for Paris 2024 track events](https://worldathletics.org/news/press-releases/repechage-round-paris-2024-olympics-budapest-entry-standards) without fixing that event's heat counts or advancement numbers in the engine.

To record starting lanes, set `THeatRoundConfig.lanes` on each qualifying or repechage round, or `THeatsConfig.lanes` with the one-round shorthand. Set `THeatsConfig.finalLanes` separately. A `THeatLanePolicy` specifies `laneCount`. To reproduce published lane assignments, supply `fixedAssignments` with one participant-and-lane pair for every entrant across that round's heats. Generation rejects missing or ineligible entrants, duplicate assignments, out-of-range lanes, and a lane used twice in the same heat. Do not combine fixed assignments with a random draw or a preference. The Paris 2024 men's 800m replay now verifies every published heat and final lane as well as the times and advancement.

Without fixed assignments, an optional full `preference` permutation of lanes numbered from 1 assigns lanes from the highest-priority entrant to the lowest; omitted preference uses ascending lane numbers. For a random draw, set `allocation = EHeatLaneAllocation.Random` and `drawSeed` instead of `preference`. Each fixture gets an independent, reproducible shuffle of all available lanes; when there are fewer entrants than lanes, some lanes remain unused. Changing the seed changes the draw for fixtures generated afterward. Each generated fixture saves its `participantId` and `lane` pairs in `heatLanes`, so loading a saved state does not redraw them. A round with more entrants in a heat than available lanes cannot be generated; increase the lane count and retry `GenerateNextRound`. This generic draw does not impose a federation's lane rules.

Equal recorded times share a heat place unless the result supplies an official `TParticipantTime.place` for every finisher. Those places can distinguish athletes on the same recorded millisecond, including at an automatic-qualification cutoff. Extra automatic qualifiers from a shared last place reduce the available time-qualification slots, following the [World Athletics place-and-time qualification rule](https://worldathletics.org/about-iaaf/documents/book-of-rules). For a tie at the last remaining time slot across heats, `EHeatCutoffTiePolicy.AdvanceAll` advances everyone tied; `RequireResolution` stops generation of the next round until the result or policy is changed, after which `GenerateNextRound` retries. The completed final determines the stage order; its timed results remain available in the saved fixture. This format records official places but does not derive them from photo-finish images or provide a cross-heat sporting tie-break for equal times.

## Stroke-play golf

Register `engine.RegisterFormat("stroke-play", New TStrokePlayScheduler, New TStrokePlayScorer)` and set the stage's `formatCode` to `"stroke-play"` with a `TStrokePlayConfig`. Define one `TStrokePlayRoundConfig` per round with its `holeCount` and optional `pars`. Each generated round fixture lists its players in `participantIds`; submit a `Custom` result with `customCode = "stroke-play-card"` and one `TStrokeScorecard` per player. A completed card normally supplies an official positive stroke count for every hole, including penalties. For individual gross stroke play with only an official round total available, set `roundStrokes` instead of `holes`; the configured `holeCount` still describes the real course. All completed cards in one round must use the same form. Round totals cannot support net or Stableford scoring, team best-per-hole, or hole countback; playoff holes still require hole-by-hole cards. A player may instead be marked withdrawn, disqualified, or did-not-start, with no official round score.

Set `scoring` to `Gross` (the default), `Net`, or `Stableford`. For net scoring, each round can define `TStrokeHandicap` entries. Supply `received` strokes for every hole, or set `playingHandicap` and a permutation of `strokeIndexes` on the round; positive handicaps receive strokes starting at index 1, and negative handicaps give strokes back starting at the highest index. This takes an already determined playing handicap as input; it does not calculate one from a Handicap Index or course rating. Gross and net totals are both retained in `TStageState.strokeStandings`.

Stableford uses the per-hole par and the player's net hole score. By default, par earns two points, birdie three, bogey one, and double bogey or worse zero. A zero on a completed card represents a picked-up hole worth zero points. Set ordered `stablefordBands` of maximum scores relative to par and `stablefordDefaultPoints` to define a different points schedule. The [Rules of Golf](https://www.randa.org/rog/the-rules-of-golf/rule-21) describe Stableford as points awarded per hole, with any handicap strokes applied before points are calculated.

For a team competition, list `TStrokeTeam` IDs and their member IDs in `teams`; each team ID must also be a competition participant. Scorecards still identify the individual members, while standings, cuts, playoffs, and advancement identify teams. `teamBestPerHole = 0` sums every member's score on each hole; a positive value counts that many best scores per hole. Gross and net modes select the lowest scores, while Stableford selects the highest point values. With a positive best count, zero can indicate that a member has no gross or net score on a hole, provided enough teammates supply scores. A count of one models the scoring principle of [four-ball](https://www.randa.org/en/rog/the-rules-of-golf/rule-23); this engine does not adjudicate the other Rules of Golf governing partners' play or scorecard certification.

Set `cutAfterRound` and `cutPlaces` to retain the leading players or teams after a round. Everyone tied on the relevant total at the last qualifying place advances by default; players or teams who miss the cut retain their earlier cards and are marked `cut`. Set `countback` to ordered `TStrokeCountbackSegment` entries, each giving `roundsFromEnd` (`0` is the final regulation round) and `lastHoles`. Equal totals are compared over those segments in order. `cutUsesCountback` also applies them at the cut line, with unresolved ties still advancing together. Net countback sums the configured per-hole net values; competitions using a different handicap fraction or matching-card procedure need rules configured for that method. The [USGA's matching scorecard guidance](https://www.usga.org/content/usga/home-page/handicapping/roh/Content/rules/Committee%20Content/USGA/LG_R7l4.htm) illustrates why the event terms must specify the method.

When the regulation lead remains tied after countback, `playoffHoleCount` generates repeated gross-stroke playoff fixtures until one leader remains. For a different extra-hole rule, set `playoffRound` with its hole count, pars, and optional handicaps, then choose `playoffScoring` as `Gross`, `Net`, or `Stableford`. A tied lead with no configured playoff stops progression; set a playoff rule and retry `GenerateNextRound`.

The [2024 Masters replay](../examples/masters_2024_replay.bmx) reads the [published final results](https://www.masters.com/pdf/2024_Final_Results.pdf) for all 89 entrants from [round-score data](../examples/masters_2024_scores.txt). It submits each official 18-hole round total to the engine, verifies the top-50-and-ties cut retained 60 players at 150 strokes (+6), and checks every final total, cut status, and shared finishing place. This replay exercises gross stroke totals and cut progression; it does not test per-hole countback, handicap allocation, or hole-by-hole rules.

## Postseason selection and seeding

`TLeagueConfig.postseason` selects playoff entrants from a completed league using named pools of divisions. Configure the number of automatic places per division, the number of remaining at-large places, and ordered tie criteria for division places, at-large places, and their seeds. The selector compares won-lost-tied percentages, including half a win for a tie, then applies criteria such as head-to-head results, division or pool records, common opponents, strength of victory, strength of schedule, combined points rankings, and scoped point differences. A multi-team at-large tie can first reduce each division to its best remaining team and use a head-to-head sweep. After a place is awarded, selection restarts for the remaining teams. If no configured rule separates a tie, selection fails instead of silently using participant ID; `TPostseasonTieDecision` can record a decision such as a drawing of lots for the exact tied set.

Set a first-round bracket's `TEntrySource.postseasonPoolCode` and its `fromStageId` to the source league. When the league completes, the engine selects and seeds that pool automatically. Seeds are kept in stage input state, so two conference brackets can have separate 1–7 rankings without changing `TParticipant.seedRank`. Subsequent bracket rounds retain those rankings; set `TBracketConfig.reseedEachRound` where the format pairs remaining teams afresh. A seven-team field fits an eight-slot bracket with one bye.

For a final that merges separate brackets, set its `TSeedingPolicy.rankingStageId` to the ID of a completed standings stage. The final then ranks its entrants by that stage's table, which can determine home advantage independently of their seeds in the earlier brackets. The named source must contain every entrant.

## Results and standings

The engine checks that a fixture exists, has not already received a result, and that a result's score, classification, or times are valid before passing it to the scorer. Group and league scorers apply configured win, draw, and loss points. Supported table tie breakers are points, goal difference, goals for, wins, points for, points against, fair play penalty units, and head-to-head points or goal difference. Rules are evaluated in order over the whole tied subset; consecutive head-to-head criteria use the same mini-table of matches among those entrants. Set `TLeagueConfig.reapplyHeadToHead` or `TGroupConfig.reapplyHeadToHead` to restart the head-to-head block for entrants still tied after that block separates some of the original entrants. If every configured criterion is equal, participant ID gives a stable display order and `sportingRank` preserves the tie. `RandomDraw` is a final decision step. Sets and games percentages require a sport-specific scorer and raise an error if configured on the built-in group or league scorer.

For limited-overs cricket, register `TCricketScorer` with a league or bracket scheduler under a `formatCode`. `TCricketConfig` sets win, tie, loss, and no-result points, balls per over, wickets per innings, and whether wins precede net run rate in a points tie. A `Custom` result with `customCode = "cricket"` carries a typed `TCricketMatchResult` with two innings, legal-ball counts, wickets, official outcome, and any revised target or net-run-rate credit. No-result innings do not affect net run rate; an all-out innings uses its full ball allocation. A custom format scorer owns its table order. To deserialize the custom config through jconv, register `TCricketConfigFactory` under the `"cricket"` config code.

A series can contain multiple event sessions with classified or timed results. `TSeriesConfig.championships` creates named standings from selected sessions; participant points can also roll up to `parentTeamId` for a team championship. Event point multipliers and eligible bonus awards are applied by the scorer. This can model several parallel rankings from one set of race results.

Series ranking uses `TSeriesConfig.tiebreakers`, or a named championship's `TChampionshipConfig.tiebreakers` when set. The built-in series ranker accepts `Points` first, optionally followed by `Wins` (number of first-place classifications) or `FinishCountback`. Countback compares how many times entrants finished in each configured position, in order. `TSeriesCountbackConfig.positions` selects positions and their priority; an empty list compares first places, then second places, and so on. `sessionCodes` limits which sessions contribute to countback. When empty, it uses the named championship's scoring sessions, or every session for the main table. A named championship can override the series countback policy. For a parent-team championship, member classifications add to the team's counts. If every configured criterion remains equal, the tied rows share `sportingRank` until a recorded table decision orders them. The decision applies to the main table or the named championship independently. A completed series qualification query uses that decided order; before completion it still evaluates possible future classifications under the scoring rules. Unsupported series tie breakers raise an error rather than silently affecting the table order.

Set `TAdvancement.championshipCode` on a series TopN route to select entrants from a named championship instead of the main series table. Set `TSeasonTransitionRule.championshipCode` for a season movement based on that board. Both wait for an explicit decision when their selection cuts through an unresolved tie. Main-series points adjustments are applied before its final rank and tie status are calculated.

`countbackSequence:TSeriesCountbackConfig[]` on a series or named championship defines ordered fallback blocks. For example, use one block with `sessionCodes = ["RACE"]` and `positions = [1, 2]`, followed by a block with `sessionCodes = ["QUALI"]` and `positions = [1]`. Race wins and second places are compared before qualifying wins. A named championship's sequence takes precedence over its single `countback` policy and the series policy; the single `countback` field remains a one-block shortcut. `Wins` uses the first block's first-place counts. A block can use a session that awards no points in the championship, and future classifications in that session still affect qualification analysis.

## Mathematical clinching

Call `TCompetitionEngine.AnalyzeClinching(comp, state, stageId, championshipCode)` to inspect a points championship. Omit `championshipCode` for the stage's main table. Built-in bounds cover series position tables (including named driver and parent-team championships) and group or league win/draw/loss points. Custom formats can supply an `IClinchBoundsProvider` through `RegisterFormatClinchBounds` or `RegisterClinchBounds`.

The result has `Clinched`, `NotCertified`, or `Indeterminate` status. `Clinched` means one participant's *minimum* final points are strictly greater than every rival's *maximum* under the remaining scheduled scoring rules. Team bounds use the best distinct finishing positions available to their eligible members. `NotCertified` means the bounds do not establish a winner; it does not prove that a rival can catch the leader. A points tie is not certified because the built-in analysis does not resolve every championship tie-break rule. `Indeterminate` identifies a missing or unbounded scoring rule in `reason`.

For a possible clinch at the next event, `nextWindowId` names the next unfinished series event or league/group round. `ClinchesAfterNext(participantId, projectedTotals)` checks supplied total points after that event against the maximum points available in later events. Pass one `TProjectedPoints` for every standings entrant. The method validates each total against that entrant's configured next-event point range. It does not generate a race classification or account for dependencies between entrants' projected totals; the caller supplies a plausible scenario or reruns the analysis after recording actual results.

A future bonus needs a finite bound: set `TBonusRule.maxPointsPerAward` and a count limit such as `uniquePerSession`, `uniquePerEvent`, `uniquePerParticipantPerEvent`, or `maxAwardsPerEvent`. Results exceeding the per-award cap are rejected before the fixture is completed. Negative series points, time-based rankings, and uncapped bonuses remain `Indeterminate` with the built-in provider. This analysis assumes no future discretionary point adjustments, penalties, or changes to the schedule and scoring definition.

## Exact qualification for points-only tables

Call `TCompetitionEngine.AnalyzeQualification(comp, state, stageId, participantId, places, groupKey, maxScenarios, championshipCode)` to ask whether an entrant can finish in the top `places`. Omit `groupKey` for a league or series; supply it for a group stage. For a named series championship, pass its code as the final argument. `Guaranteed` means the entrant occupies a place in every valid points scenario. `Eliminated` means it cannot occupy one. `Possible` means there are both qualifying and non-guaranteed scenarios. The `qualifyingScenario` and `failingScenario` fields show example fixture outcomes.

For leagues and groups, the solver enumerates the three possible point outcomes of each remaining match together, so opponents cannot both receive win points from their shared fixture. An outcome's `result` is `1` for a home win, `0` for a draw, and `-1` for an away win. For a position-table series, it enumerates every non-empty ordered subset of stage entrants accepted as a classification. An outcome's `classificationOrder` lists those entrant IDs. A finishing place can be awarded only once in a session. Session scoring overrides, event point multipliers, named championships, and parent-team point totals use the series scorer's rules.

League and group qualification still requires points-only ranking; tie breakers that need future scorelines return `Indeterminate`. Series qualification applies its configured points and countback rules to both completed and projected classifications. A tie left unresolved by every configured rule gives each tied entrant a possible place but none a guaranteed place at the boundary. A remaining series session with bonus awards or non-position scoring returns `Indeterminate`. The same status is returned if the search reaches `maxScenarios` before proving an answer. A large series can have very many possible classifications; independent bounds on points and countback can prove some answers without enumeration and prune entire search branches. Equivalent series states are evaluated once, so `scenariosExamined` counts distinct projected ranking states checked, rather than every classification order generated. Existing standings adjustments are included; future discretionary adjustments and schedule changes are outside the search.

`TCompetition.seasonTransitions` projects promotion and relegation into `TSeasonMovement` records through `ResolveSeasonMovements`. Rules can select teams from a completed league or playoff stage and name their destination division. The caller uses those records when creating the next season.

## Knockout match outcomes

`TBracketConfig.matchFormat.bestOfMatches` schedules an odd number of games per tie. A side wins the series on a majority of games; later scheduled games are cancelled when it clinches. Games must be recorded in order. `TSchedulePolicy.venuePolicy.seriesTemplate.pattern` supplies alternating blocks of home games: `[2, 2, 1]` produces home, home, away, away, home for the higher seed in a best-of-five tie. Without a pattern, home advantage alternates by game.

For a single score-based match, a tied score needs a configured and recorded decider. A two-leg tie first uses aggregate score and, if enabled, away goals. When it is still tied, the deciding leg can carry a penalty score if `matchFormat.penalties` is enabled. `afterExtraTime` records that the submitted match score includes extra time and requires `extraTimeMinutes` in the format. A tied final result with no winner is rejected before the fixture is completed.

With `TMatchFormat.setRules`, a bracket also accepts a completed `SetBased` result. It validates set winners, the configured set target and margin, optional game-score tie-break exception, and the required number of sets to win the match. `bestOfMatches` can be combined with set-based matches, so a team tie can consist of several individual matches. Set `TResultPayload.retiredParticipantId` when a player retires; the other player advances even if the recorded completed sets favour the player who retired. The final `TSetScore` may be partial, and the retirement and winner survive state serialization.

The [2011 Cricket World Cup replay](../examples/cricket_2011_replay.bmx) derives innings totals from [Cricsheet's ball-by-ball data](https://cricsheet.org/downloads/) and records all 49 matches. Its configurable limited-overs scorer awards points for wins, ties, and no-results; calculates net run rate using legal deliveries, full overs for all-out innings, and credited totals for a rain-adjusted target; and selects four qualifiers from each group. Fixed bracket slots reproduce the published quarter-final pairings and path to India's title. The replay checks both seven-team group orders and key net run rates. [Cricsheet's Open Data Commons Attribution License](https://cricsheet.org/licensing/) applies to the transformed [replay data](../examples/cricket_2011_replay.tsv).

These are historical acceptance cases, not a claim that all regulations of every event are modeled. The 2026 soccer replay does not calculate FIFA's fair-play or drawing-of-lots fallbacks if all recorded group tie breakers stay equal. Wimbledon tie-break point scores and point-by-point play are not captured by the set-score replay. The MLB replay imports the historical regular-season fixture list; it does not generate MLB's calendar. Its configured tie criteria suffice for the 2024 playoff field, but later MLB fallbacks such as the last half of intraleague games are not yet implemented. The cricket scorer covers limited-overs matches; Test cricket declarations, follow-ons, drawn matches, and super overs require further result rules. The sailing scorer records official race scores and statuses; it does not decide protests, redress awards, or whether a race committee should abandon a race.

## Current boundaries

The engine does not provide a universal rule language for every sport. Set-based results resolve a match, including retirement, but point-by-point tennis scoring, tie-break points, and final-set variants are not modeled. Extra-time minutes are configuration and result metadata; the engine does not track a match clock. Swiss pairing has a generic search and a partial Dutch-style search, neither a complete named FIDE pairing algorithm. Its Buchholz calculation supports the described unplayed rounds but not all FIDE eligibility and entry cases or Sonneborn-Berger. Timed heats can assign lanes, but do not model event-specific repechage eligibility exceptions. The default calendar compares equal time strings rather than fixture duration or time-zone overlap. Joint planning covers generated fixtures from started stages, especially independent roots; it cannot pre-plan entrants or fixtures that depend on future results. Weeks are searched with slots for league stages with a configured length or fully week-numbered calendars; other formats retain their existing week or round assignment. A failure message gives one blocked fixture and candidate reasons, not a minimal explanation of every conflicting rule. The tree builder covers power-of-two single and double elimination plus placement ladders for single elimination. Nonstandard lower brackets and other consolation structures still require explicit stages and routes. Some advanced draw constraints are still work in progress. Use registered format, week, and slot implementations for rules beyond the built-ins.

Postseason tie criteria use the recorded match scores. Criteria needing other match statistics, such as the NFL's net-touchdown fallback, require a custom selector or a recorded decision if reached. A recorded decision is tied to the exact remaining teams and carries a reason. The 2024 NFL replay does not need either fallback. In-season playoff-clinching scenarios under these postseason rules are not yet analyzed by the points-only qualification solver.

Series and Swiss standings store integer units using `pointsScale`, which must be chosen before scoring. Exact decimal string overrides are available for Swiss win, draw, loss, bye, and planned unplayed awards. The earlier `Float` Swiss fields and series event multiplier remain supported for existing definitions; new fractional rules should use the `*Exact` fields. Group and league win/draw/loss awards still use whole integer points. A scale too small to represent an exact award is rejected rather than rounded.

Run the module tests from `tests` after building `tests/test.bmx` with `bmk makeapp -r`. The tests cover graph advancement, fixture and result validation, league rules and byes, venue conflicts, standings, mathematical clinching, season movements, custom serialization, and group and bracket behavior.
